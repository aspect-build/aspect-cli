# Bazel-ify this Scala repository

Inspect `build.sbt`, `project/` definitions, `project/build.properties`, plugins, resolver and credentials policy, Scala and sbt versions, cross-build settings, compiler options, semanticdb/compiler plugins, source and resource roots, generated code, test framework, assembly or packaging steps, and CI before changing BUILD files. Preserve the useful sbt workflow while introducing Bazel incrementally; do not replace it wholesale.

Use the bundled Scala recipe as the default. Begin with one independently meaningful `scala_library`, `scala_binary`, or `scala_test`; declare only its direct first-party and Maven dependencies, resources, runtime data, and Java interop. Keep the target in the closest directory owning its sources. Do not allow a root BUILD file to recursively absorb `src/main/scala`, `src/test/scala`, managed sources, generated protobuf/Thrift trees, or sibling sbt subprojects.

Select the repository's exact Scala line before creating the toolchain. Preserve cross-build variants as distinct target sets, retaining their compiler options and dependency coordinates. Model macros, compiler plugins, generated sources, test-framework runners, and resource lookup explicitly. A source file compiling under Scala 2.13 says little about its Scala 3 alter ego; the compiler is not obliged to be sentimental.

Do not wrap `sbt test`, `sbt assembly`, or a task that writes source or managed output as a final Bazel target. First model the tool's declared inputs and outputs, then add the framework-specific rule or action after the representative source target works. Treat Play, Spark, Scala.js, Scala Native, Akka, code generation, fat-JAR assembly, and publish workflows as separate migrations with their own runtime and packaging validation.

Validate each stage with the repository's existing sbt command alongside the equivalent Bazel target. Compare selected Scala version, compiler options, macro/plugin behaviour, dependency eviction, generated output, test discovery, resources, runtime classpath, and package contents. Report unresolved differences rather than hiding them behind host caches, broad tags, or local-only configuration. Once the representative path works, report whether the repository is ready for the separate remote-configuration prompt. Do not configure remote caching or build-event streaming as part of this migration.
