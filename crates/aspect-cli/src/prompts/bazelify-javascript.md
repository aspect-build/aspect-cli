# Bazel-ify this JavaScript or TypeScript repository

Inspect the root and nested `package.json` files, workspace declaration, lockfile, package-manager configuration, Node version policy, scripts, generated source, bundler, test runner, browser assets, and CI before changing BUILD files. Preserve the useful package-manager workflow while introducing Bazel incrementally; do not replace it wholesale.

Use the bundled Aspect JavaScript and TypeScript recipe as the default. Start with a representative library, CLI, or TypeScript compilation target whose dependency closure is independently meaningful. Add `npm_link_all_packages` at the package-manager root and at each workspace package that needs npm dependencies. Create explicit `js_library`, `js_binary`, `js_test`, or `ts_project` targets with only their direct first-party and `:node_modules/...` dependencies. Keep first-party workspace packages explicit through `npm_package(name = "pkg", ...)`, and keep generated files, static assets, test fixtures, code generation, Node-native modules, and platform constraints declared rather than relying on an ambient `node_modules` tree.

The package manager remains the source of dependency intent and the committed lockfile remains the source of resolved versions. For pnpm, `npm_translate_lock` consumes `pnpm-lock.yaml`; update it through the declared pnpm version and inspect the lock diff. For Yarn or npm, do not fabricate a pnpm lock simply because Bazel needs one. First establish a reviewed compatibility path that preserves workspace links, patches, overrides, plugin behaviour, peer resolutions, and lifecycle scripts. If that is not available, stop after the source-target slice and report the dependency-resolution blocker.

Do not wrap `yarn build`, `npm run build`, `npx`, or a script that writes back into the source tree as the final Bazel target. First use the tool's declared binary through a `js_run_binary` or framework-specific rule with declared inputs and outputs. Treat framework migrations separately: a Next.js, Vite, Webpack, Jest, Storybook, or browser-asset build is complete only after its output directory, configuration, assets, runtime dependencies, and representative run or test are declared and validated.

Hand-author the first package targets. Do not use an unconfigured generator as a substitute for reviewing imports and package boundaries. If a suitable JavaScript or TypeScript generator is later introduced, run it in diff mode over one explicit source root, review every dependency and source-list change, then apply selectively.

Validate each stage with the repository's existing package-manager command and the equivalent Bazel target. Report differences in module resolution, generated output, platform-specific dependencies, lifecycle hooks, and test or bundler behaviour rather than hiding them behind local-only configuration. After a representative path works, report whether the repository is ready for the separate remote-configuration prompt. Do not configure remote caching or build-event streaming as part of this migration.
